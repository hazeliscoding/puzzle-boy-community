# Roadmap

Puzzle Boy Community Edition is a standalone puzzle game on the Puzzle Boy rules, with its own stages, art and sound. This file tracks the decisions already made, what gets built and in what order.

## Decisions (2026.10.14)

- **Instant play comes first.** An unpacked release starts on a machine with no Nocturne, no Steam, no .NET, no network and no dev checkout, and reaches a playable stage. It never opens on a missing-assets screen.
- **No Atlus content.** No art, audio, text, models or UI from Nocturne, no Manikin Kid, no Nocturne dialogue and no original stage layout, not even converted to JSON. Importing from the player's own install is optional and comes last (C4).
- **The rules come from puzzle-boy-engine,** pinned as a git submodule at `external/puzzle-boy-engine`. `.gitmodules` names the GitHub URL; until the engine is published, a local clone overrides it in `.git/config` (AGENTS.md, Commands), and CI can't check out.
- **Content is data beside the executable.** `content/` is copied next to the game on build and publish. Every file in it has an entry in `content/provenance.json` with its creator, source, license and redistribution status, and `content/ASSET_CREDITS.md` credits it for people.
- **C# on .NET 10 with MonoGame (DesktopGL),** like the preservation port. Text is drawn with FontStashSharp (MIT) from TTFs read at runtime: Atkinson Hyperlegible for body text and Silkscreen for titles, both SIL OFL 1.1. Graphics are drawn in code (lit boxes, outlines, and a pattern per group so color is never the only cue), and sound is synthesized at startup.
- **Pixel Jack is the player character,** grown from the 16×16 brand mark (puzzle-boy's `docs/brand/`). It must not resemble Nocturne's Jack-o'-Lantern.
- **Stage ids belong to a pack** (`first-steps/nudge`), never to a Nocturne file number.
- **Every bundled stage has a recorded solution** in the tests, replayed against the engine's `Board`.

## Decisions (2026.10.15)

- **Original content is Apache-2.0, like the code,** credited to the Puzzle Boy Community authors. That covers the stages, the theme and Pixel Jack, which puzzle-boy's `docs/brand/` already ships under Apache-2.0. Apache-2.0 grants no trademark rights (section 6), which suits a brand mark.
- **Provenance.** `content/provenance.json` has one entry per file or glob (`*` within a folder, `**` across): `path`, `creator`, `source`, `category`, `license` (SPDX), `modified` and `redistribution`, which must be `allowed` to ship. A file by anyone but the Puzzle Boy Community authors needs its own entry with a `sha256`, so a changed font fails the tests. Every file must be covered and every entry must match a file. The stages entry covers only `stages/**/*.json`, and a pack folder may hold nothing but its `pack.json` and the stages it lists, so a stray file is never shipped as an original stage.
- **Pack format, schema version 1.** `pack.json` has `format` `puzzle-boy-pack`, `schemaVersion`, `packId`, `title`, `creator`, `license` and up to 200 `stages`, each with an `id`, a `title` and a `file` relative to the pack folder. Ids are 1 to 48 of `a-z`, `0-9` and `-`, unique in their pack; a stage's full id is `packId/id`. A higher `schemaVersion` fails with "made by a newer version". Paths are relative, use `/`, never contain `.`, `..` or a colon, and never pass through a link. `pack.json` and each stage are at most 64 KiB. A bad stage is reported and left out; the rest of the pack still loads.
- **Known layouts are caught by fingerprint.** `LayoutFingerprint` (version 1) hashes a stage's cropped tile grid in its smallest rotation or mirror, with and without the goal and starts. The 100 fingerprints of the 50 Nocturne stage files are in `scripts/known-atlus-layouts.txt`, generated outside the repo from a local install.
- **A stage tool for designers.** `tools/PuzzleBoy.StageCheck` validates, solves and fingerprints a stage or a pack. The solver is breadth-first over every input (four steps and, with two characters or more, a switch), so a solution has the fewest inputs; it reports the pushes and turns in it too. The engine's `Board` makes every move: a state is the cells and the visible characters from the active one, turned back into a stage to resume from, and a test checks that round trip against a live board on random walks. States are deduplicated by 128 bits of SHA-256. The default cap is 2,000,000 states, about 13 seconds on the owner's machine, and reaching it is reported as "search limit reached", never as unsolvable.
- **`--smoke-test` needs no window.** It runs the same checks as the content tests on the `content/` beside the executable, measures text with each font through FontStashSharp (which needs no graphics device for that), and takes one step on the first stage. CI runs it on the built game. A WinExe has no console on Windows, so there the report shows only when output is redirected; the exit code always works.
- **A stage may carry a hint.** A pack's stage entry can add a `hint` of up to 200 characters, which the help screen in play shows, and which the stage's intro shows under its name until the first step while the stage isn't cleared. A longer one leaves the stage out with a problem, like any other bad entry.
- **Screens are a stack.** Title is always at the bottom, so Back never quits; Quit to Title clears the stack, and finishing a pack returns to stage select. Screen logic, menu focus and input mapping are plain classes with tests; drawing isn't tested.
- **Input follows the view,** as in the original: direction = (screen direction - view turns) mod 4, the preservation port's formula. A step waits for the last one's animation (4 ticks a walk, 5 a push or turn, 9 with a fall) and for a turn of the view to land.
- **`--smoke-gui` runs by hand for now.** It needs a display, so CI doesn't run it until C5 adds one. Run it after a visual change and look at both pictures.
- **The campaign is `first-steps`: 20 original stages,** ordered walk, push, holes, multi-cell blocks, swivels, the switch tutorial (Make Way), combinations, and the finale (Long Way Round). They replace the three placeholder starters, which taught the same first ideas with less to solve. Candidates that repeated another stage (a second relay shaft, a second ordering puzzle, a turn cycle run twice, a swivel stage that was mostly pushing) were left out. The stages stay Apache-2.0 under the decision above, which already lets players remix them.
- **Saves are one JSON file, `save.json`,** in `%APPDATA%\PuzzleBoyCommunity`, `~/Library/Application Support/PuzzleBoyCommunity` or `$XDG_DATA_HOME/puzzle-boy-community` (`~/.local/share/puzzle-boy-community` without it), or in the folder `--data-dir` names. Smoke runs use a fresh temp folder, never the player's. A write goes to `save.json.tmp`, is flushed, then replaces `save.json` with `File.Replace`, which keeps the old one as `save.json.bak`. A damaged save is copied to `save.json.damaged` and the backup loads, else defaults; either way a notice shows over the game for a few seconds and play goes on. A save from a newer schema, or one that can't be opened at all (another program holding it), is left untouched and this run doesn't write; the second loads the backup or defaults.
- **Save schema 1** holds `settings` and `stages`, a map from stage id to `completed`, `bestMoves` and `bestTime` (seconds, from the stage starting to the clear, pauses excluded). Schema 0, `{ "cleared": [ids], "volume": 0..1 }` with no `schemaVersion`, is a test fixture that no release wrote: it keeps the migration path tested until a real schema 2 exists. It migrates to completed stages with no best, whose next clear sets the first best, and one volume for music and sound. Values out of range are brought back in on load.
- **A pack unlocks in order, with one skip:** its first stage, every cleared stage and the two stages after each cleared one, so a player stuck on one stage (Single File, say) can go on to the next chapter, but never skip two in a row. Play starts the first unlocked stage not yet cleared, in pack order, or the last stage once all are cleared.
- **Settings apply at once and save on each change.** Fullscreen is borderless at the desktop's size. Window size is 75% to 200% of 1280×720, shrunk to 90% of the display when it wouldn't fit there, and the setting shows the size the window really gets. UI scale (90% to 120%) enlarges body text and the small Silkscreen labels (18 px and under: HUD labels, stage counters, status words); headings and the layout stay put. Reduce motion stops the drifting blocks, the title bob, the stars, the menu glow, the confetti and camera easing; steps still slide. High contrast draws text and panels opaque, hides the drifting blocks, and gives the board a flat lighter floor, ink walls and black pits.
- **The play camera shows the whole play area.** It looks at the middle of the stage and, every frame, backs off just far enough (never nearer than 9 cells) that the play area's corners, up to the height of what stands on it, land between the HUD's stat panels and its hint bar (y 120 to 668 of 720), so turning the view or resizing the window reframes it. A test checks every bundled stage's cells and goal from each turn and overhead; `--smoke-gui` showed Footbridge, Plank Run, Shape Sorter and Single File whole (2026.10.15). It replaces following the character on stages wider than 12 or deeper than 9.
- **A restart can be undone.** R sits beside E, and a late stage takes up to 161 moves, so Undo with nothing left since a restart brings back the board, the move count, the undo history and the clock from before it. It works the same from the pause menu and the pad.
- **Antialiasing is optional.** Some GL drivers, such as Mesa under WSLg, offer no multisampled context, and MonoGame then can't create a device. The game retries once without multisampling and says so on stderr; if that fails too, it explains on stderr and exits 1. A self-contained linux-x64 publish passed `--smoke-gui` under WSLg (Ubuntu 24.04, Mesa 25.2.8) this way, so WSLg is a tested configuration (2026.10.15).
- **`--smoke-gui-screens <dir>`** walks the title, stage select, settings, play, pause and help through the real menus and saves each as a PNG, for checking a visual change and for the README.
- **The level editor works on the engine's `StageBuilder`** and checks with its `Validate`, so the editor, the stage tool and the packs agree on what a stage is. Its logic (`StageEditor`, `EditorView`, `CustomStages`) is plain classes with tests; the screen only draws and routes input. The canvas is top-down with +y up the screen, as play shows it, and coordinates are the engine's `(x, y)`.
- **A group's number and its look are separate.** The editor shows each part's group number on it as well as its color and pattern, since 7 colors and 8 patterns repeat. Painting never changes another cell's group, and N picks the lowest group no tile uses (1 to 35, the most the stage JSON writes), so two groups never merge by accident. A group stays one kind: a block can't be painted into a swivel's group, nor a second center.
- **Editor undo is its own,** apart from play's 30 steps: up to 200 changes, a whole stroke or rectangle is one, and undoing back to the saved stage makes it clean again.
- **A stage is saved only when it has no problems,** so every saved stage plays. Saves are engine stage JSON in `<data dir>/custom/<name>.json`, written to a temp file and moved over. The name comes from the title on the first save: accents dropped, lowercase ASCII letters and digits, every other run one dash, at most 48 characters, `stage` when nothing is left, `-stage` after a Windows device name such as `con`, and `-2`, `-3` when taken. Renaming keeps the file, so progress stays with it. Delete asks first and drops the stage's progress; closing a stage with unsaved changes asks too, and so does closing the window (X, Alt+F4) while editing or playtesting it, through MonoGame's `Exiting` event; `--smoke-gui-screens` closes the window over an unsaved split and checks that it asks (2026.10.15). Invalid drafts can't be saved yet.
- **Playtest goes through the play screen** with a stage built from the editor, so the shared `Board` and session run it and the document is never touched. Nothing is recorded. Esc or a clear returns to the editor with the stage, cursor and undo history as they were; P pauses.
- **Solve (capped) searches at most 250,000 positions** in the background with the stage tool's solver, now in `Play/`. Reaching the cap reads "Search limit reached (not proven unsolvable)", never unsolvable, and a result for a stage changed since is dropped.
- **My Stages is a tab of stage select,** after the bundled packs. Its stages have ids `custom/<name>`, are always open, and save progress like any other.
- **A level pack is a `.zip` in the built-in pack format:** `pack.json` and `stages/*.json`, nothing else ([docs/packs.md](docs/packs.md)). Export, from a stage's actions in the editor's list, writes the ticked stages to `<data dir>/exports/<packId>.zip` through a temp file, the id made from the title as a stage's name is; the license is CC0-1.0 unless the player picks CC-BY-4.0, CC-BY-SA-4.0 or Apache-2.0. There's no native file dialog: the title and creator are typed in the game, and the screen shows the folders' full paths.
- **Import checks everything before it writes.** Stage select's last tab, + Import, lists the `.zip` files in `<data dir>/imports`; `--import-pack <zip>` does the same from a command line. An archive is refused over 2 MiB, 256 entries, 64 KiB unpacked in an entry or 4 MiB in all; for an absolute, drive, UNC, backslashed or colon path, a `.`, `..` or empty part, a link, a name twice (ignoring case), another archive or any file but `pack.json` and `stages/*.json` (a `.md` or `.txt` is left out with a warning); and for a `pack.json` or stage that the content loader rejects, or a stage whose fingerprint is a known Nocturne layout. The checks run in a scratch folder outside the data folder; the pack then moves into `packs/<packId>` with one rename. A built-in pack's id is refused; an imported one's asks: replace it (progress stays) or keep both (`-2`). The known-layout list is copied beside the game for this, and without it nothing is imported or exported.
- **Imported packs are tabs** between the bundled packs and My Stages, marked imported with their creator and license. They unlock in order like a bundled pack and save progress under `packId/id`.
- **Classic import is stages only, and only on request.** (The stages-only part is superseded by the classic asset pack below; the import is still only on request.) Settings → Import Classic Content, or `--import-classic <folder>`, finds the player's own Nocturne HD Remaster (beside the game, in any Steam library, or a typed folder holding `smt3hd.exe`, a copy of `smt3hd_Data`, or copied bundles), reads the `pazzleboy` bundle, checks each stage file the two lists use with the engine's `Stage.Parse`, and stores the raw bytes in `<data dir>/classic/stages/` with an `index.json` of the source, the date and each file's SHA-256. A missing or damaged copy gives a message and writes nothing; an earlier import stays. Remove Classic Stages deletes the folder after asking and keeps the progress. The reader is adapted from puzzle-boy's `GameInstall` and is the only code that uses AssetsTools.NET (MIT); IL-walking tests show the title and content loading never reach `Classic/`, and that only the import screen and its command start an import. The import screen is reached from Settings only, never at startup or from stage select.
- **The classic campaigns are tabs after the imported packs.** Classic: Original 20 plays files 2, 4, 32, 8, 38, 36, 37, 48, 42, 49, 40, 20, 22, 13, 21, 24, 14, 10, 25, 26 (puzzle-boy's `OriginalStageOrder`), and Classic: Bonus the 23 solved unused files 1, 30, 31, 0, 3, 9, 35, 43, 5, 6, 33, 7, 19, 47, 39, 41, 45, 34, 12, 46, 15, 11, 44 (puzzle-boy's ROADMAP M4, `PlayOrder.Bonus` at `pre-split-baseline`). Ids are `classic/original/NN` and `classic/bonus/NN` by file number, so progress survives a re-import. They unlock like any pack, with the one skip, since the original is a campaign too. A file that's missing, changed since the import or unreadable is left out with a notice; the rest play. They're never the player's stages, so the editor's export can't reach them, and a copy of one is refused by its fingerprint.
- ~~**No classic theme for now.**~~ Superseded by the Classic Nocturne theme decisions below (2026.10.15). Board textures, backdrop and music from the player's install would need puzzle-boy's texture and audio readers (Fmod5Sharp, NVorbis, DXT decoding) in this game. The default theme is complete, and stages alone keep the compatibility module small, so the classic look moves to Later.

## Decisions (2026.10.15, releases)

- **Version 0.1.0.** The game's csproj holds `<Version>`; the informational version adds the commit, which the credits and `--smoke-test` show as `0.1.0+<7-character sha>`. A release tag must be `v` plus that version, or the release workflow stops.
- **Archives are built on Linux** by `scripts/package.sh`, one per runtime, self-contained, files at the archive's root beside `content/`, `LICENSE`, `THIRD_PARTY_NOTICES.txt` and `known-atlus-layouts.txt`. Windows gets a `.zip`, the rest a `.tar.gz` whose modes the script sets (the game 755), so a Windows build of the tarballs keeps the executable bit too. `SHA256SUMS` lists every archive; the smoke jobs and the release check the same bytes against it.
- **`scripts/check-archive.sh` reads an archive without unpacking it,** so a bad path can't land anywhere, and requires what the manifest lists rather than a fixed file list. It refuses the formats `check-content.sh` refuses, by name and first bytes, so a release can never carry a Nocturne bundle, including from a later Classic theme.
- **Release smoke runs on each system's own runner,** unpacked into an empty profile outside the workspace: `windows-latest`, `ubuntu-latest`, `macos-latest` (arm64) and `macos-15-intel` (GitHub's last Intel image, until August 2027). Linux must open the window under Xvfb. Hosted Windows and macOS runners may have no OpenGL, so there a missing OpenGL window shows as a failed step with the warning "GUI not verified on this runner" and the job goes on; any other GUI failure fails the job. The tag publishes only after every smoke job passes.
- **Builds are unsigned** apart from the SDK's ad-hoc signature on the macOS executables. The release notes say so and how to get past SmartScreen and Gatekeeper; they also say the Classic Nocturne theme is optional, from the player's own copy, and comes in a later milestone.

## Decisions (2026.10.15, Classic Nocturne theme)

The owner's direction, superseding "No classic theme for now" above.

- **Community is the Nocturne Puzzle Boy minigame, expanded,** not a visual reimagining. It keeps its own title, stage select, settings, saves, editor, packs and stages, and plays them in the original's look and sound when the player has their own copy.
- **The Classic Nocturne theme is primary and first-class:** the original board atlas, glass walls and outlines, the Jack-o'-Lantern model with its idle, facing, shadow and glow, the `BG_pzl` backdrop, the follow camera with its quarter turns, overhead view and fall shake, the move timing, and the original effects and music. It gets the same tests, smoke runs and docs as the Default theme, except what would need Atlus files in CI.
- **The Default theme stays the standalone fallback,** complete and unchanged: procedural art and synthesized sound. Releases ship only it, so a release still plays out of the box.
- **The presentation code is shared, not copied.** puzzle-boy-engine's `PuzzleBoy.Nocturne` (bundle reading, `GameInstall`) and `PuzzleBoy.Rendering` (`BoardView`, `CharacterModel`, `ViewCamera`, `MoveAnimation`, `Sounds`) are what puzzle-boy draws with. Community's copied install reader goes. Only `Classic/` uses them, and startup and the Default theme never do.
- **Classic assets come through an asset provider:** a classic pack folder, whose `origin` is `local-import` (built from the player's own install) or `licensed` (a properly licensed package the player points at, showing its licensor and license). The live install is read only while importing. Nothing is downloaded, and nothing is fetched or bundled by the build.
- **The classic pack is a portable folder made on the player's machine:** the exact bundle files the Classic theme reads, copied byte for byte under `smt3hd_Data/StreamingAssets/PC/`, so the engine's `GameInstall.At` reads it unchanged, plus `classic-pack.json` (`format` `puzzle-boy-classic-pack`, `schemaVersion` 1, `origin`, `createdFrom`, `created`, each file's size and SHA-256; a licensed pack adds `licensor`, `license` and `evidence`). Sizes and hashes are checked before use. It lives in `<data dir>/classic`, replacing M6's stage-only layout, and stage ids stay `classic/original/NN` and `classic/bonus/NN`. An exported zip carries it to the player's other computers. shortcut: bundles are copied whole (about 85 MB, mostly `common`), not re-encoded; extract only what's drawn if the size ever matters.
- **No redistribution.** No classic pack, bundle or `classic-pack.json` enters `content/`, the repo, a release or a level pack. An exported pack says it was made from the player's own copy for their own computers and must not be shared. Distributing a licensed pack stays out until the rights are settled.
- **No Manikin Kid and no Nocturne dialogue,** in either theme. The Classic theme reads no text bundle; Community's HUD, pause menu, help and clear flow sit over the original board.
- **Theme setting: Auto (the default), Classic or Default.** Auto plays Classic when a valid classic pack is there and Default otherwise. When the pack is missing or fails its check, play falls back to Default with a notice that says why; it never stops the game. The theme only picks the presenter: rules, stage ids, move counts, undo and saved progress are the same in both.
